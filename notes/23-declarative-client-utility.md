## 1. Understand the four files

| File | Responsibility |
| --- | --- |
| ../client/ask.rb | OptionParser validation and Ruby HTTP requests. |
| ../client/kustomization.yaml | Instructions for generating the ConfigMap from ask.rb. |
| ../k8s/service-client.yaml | Client Deployment, labels, container, and ConfigMap mount. |
| ../bin/ask | Executable launcher forwarding arguments to Ruby inside the client. |

```text
WSL: ./bin/ask -o a -p /seat
  -> kubectl exec deployment/service-client -c client
    -> ruby /tools/ask.rb -o a -p /seat
      -> HTTP from the client Pod to Service office-a:4567
        -> office A Pod
```

The request originates inside the cluster. This exercises Service discovery and the normal client network path used in our NetworkPolicy experiment. Ruby is available in the client image, so no host Ruby installation is needed. The launcher is a tracked file, not a shell function that every reader must recreate.

## 2. Inspect the source and options

```bash
cat client/ask.rb
cat bin/ask
```

The utility accepts --office/-o, --path/-p, --data/-d, and --help/-h. Office must be a or b; path must be /health, /seat, or /book. Data must parse as a JSON object. Without data it sends GET; with data it sends POST and sets Content-Type: application/json.

OptionParser handles option syntax and office choices. Our additional checks require office and path to actually appear, reject leftover arguments, validate the path, and validate JSON. Declaring an option that takes a value does not itself make that option mandatory.

The utility does not enforce every endpoint/method combination or the application's customer rules: for example, GET /book can still receive an application response rejecting that method. It prints HTTP status and body so the user can inspect the result.

| Utility exit code | Meaning |
| --- | --- |
| 0 | HTTP response received, including 409 or 503; also successful help output. |
| 1 | A caught transport/connection failure. |
| 2 | Invalid arguments or JSON. |

A successful utility exit does not prove a successful booking. Read the printed HTTP code. Kubectl itself can also fail before Ruby starts; its error is a separate layer.

The request has connection, read, and write timeouts of 2, 10, and 5 seconds, respectively. These are not one overall end-to-end deadline. Automatic Net::HTTP retries are disabled to keep the experiment to one request attempt. A transport failure does not prove a POST was never processed.

## 3. Generate the ConfigMap declaratively

```bash
cat client/kustomization.yaml
kubectl kustomize client/
```

The second command previews the generated YAML without applying it. The tracked recipe contains:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: cap-lab
configMapGenerator:
  - name: service-client-tools
    files:
      - ask.rb=ask.rb
generatorOptions:
  disableNameSuffixHash: true
```

The left ask.rb is the ConfigMap key. The right ask.rb is the source file relative to the client directory. This retains one editable Ruby source instead of duplicating the entire script in a handwritten ConfigMap.

Kustomization is a local build recipe understood by kubectl; the cluster receives an ordinary ConfigMap. The fixed name matches the separate Deployment's configMap.name reference. Disabling the name suffix also means a script update will not change that reference and trigger a Deployment rollout automatically.

Apply the ConfigMap before the Deployment needs to mount it:

```bash
kubectl --context=k3d-cap-kub-lab apply -k client/
```

The namespace comes from kustomization.yaml. This command only applies the resources generated by that directory; it does not also apply the separate client Deployment.

## 4. Deploy the client

The committed manifest uses ruby:4.0.6-alpine and imagePullPolicy: IfNotPresent. Each node downloads the image if missing from its own image store. Docker's host image cache and k3d nodes' image stores are distinct. The command ruby -e sleep keeps the container available; it does not start another booking office.

If the old standalone Pod named exactly service-client still exists, remove it once:

```bash
kubectl --context=k3d-cap-kub-lab -n cap-lab \
  delete pod service-client --ignore-not-found
```

The Deployment creates Pods with generated suffixes, so this command targets the earlier standalone Pod. Do not delete the office Pods.

```bash
kubectl --context=k3d-cap-kub-lab \
  apply -f k8s/service-client.yaml

kubectl --context=k3d-cap-kub-lab -n cap-lab \
  rollout status deployment/service-client --timeout=180s

kubectl --context=k3d-cap-kub-lab -n cap-lab \
  get pods -l app=service-client --show-labels
```

Expect one ready client Pod with app=service-client and role=client. The app label connects the Pod to the Deployment selector. The role label connects it to our NetworkPolicy's allowed sources. Replacement Pods inherit both labels automatically.

No client Service is needed: this container initiates HTTP requests rather than listening for them. Kubectl exec reaches the container through Kubernetes administration APIs.

## 5. Connect the mount names

In the Pod specification:

```yaml
volumes:
  - name: client-tools
    configMap:
      name: service-client-tools
```

In the container specification:

```yaml
volumeMounts:
  - name: client-tools
    mountPath: /tools
    readOnly: true
```

The shared name client-tools connects the mount to the Pod volume. The ConfigMap name connects that volume to the stored resource. The key ask.rb becomes the file /tools/ask.rb.

/tools is an arbitrary descriptive directory inside the container, not a special Kubernetes directory or a WSL folder. Kubernetes makes the mount available there; no Dockerfile mkdir is required. Changing it to /client would require the launcher to use /client/ask.rb. A dedicated directory avoids hiding existing image files under the mount.

This is a read-only volume containing an uploaded copy of the script, not a live connection to the WSL source directory. We mount the whole directory rather than using subPath.

</details>

## 6. Verify the utility

The launcher was committed executable (Git mode 100755). If permission was lost locally, restore it with chmod +x bin/ask. Run from the repository root:

```bash
kubectl --context=k3d-cap-kub-lab -n cap-lab \
  exec deployment/service-client -c client -- \
  ruby -c /tools/ask.rb

./bin/ask --help
./bin/ask -o a -p /health
./bin/ask -o b -p /health
./bin/ask -o a -p /seat
./bin/ask -o b -p /seat
```

Expect Syntax OK, readable help, and HTTP 200 for health and seat reads. If the prior experiment's offices have not restarted, the seat reads should still show both conflicting bookings. Do not treat that state as guaranteed after an unrelated restart.

Check validation:

```bash
./bin/ask -o c -p /seat
./bin/ask -o a
./bin/ask -o a -p /book -d 'not-json'
```

Expect argument errors without HTTP requests. When the seat is already occupied, check the POST path:

```bash
./bin/ask -o a -p /book -d '{"customer":"Charlie"}'
```

Expect HTTP 409. If the seat is empty, this would instead create a booking: inspect the preceding reads first.

The launcher uses "$@" to preserve argument boundaries, including JSON containing spaces. Shell exec replaces the launcher process with kubectl; kubectl exec then runs Ruby in the selected Deployment Pod. No generated Pod name needs to be copied into the script.

## 7. Update the script predictably

After editing client/ask.rb:

```bash
kubectl kustomize client/
kubectl --context=k3d-cap-kub-lab apply -k client/

kubectl --context=k3d-cap-kub-lab -n cap-lab \
  rollout restart deployment/service-client

kubectl --context=k3d-cap-kub-lab -n cap-lab \
  rollout status deployment/service-client --timeout=180s

./bin/ask --help
```

Preview checks the generated resource; apply uploads the new contents. Restart requests a replacement client, and waiting ensures the rollout completes before testing. Neither command changes the office Deployments or their records.

Restart is optional for this whole-directory ConfigMap mount: Kubernetes eventually refreshes mounted files, and each invocation starts a new Ruby process that reads the script. Restart-and-wait gives this lab a predictable update boundary rather than assuming the refresh happened immediately. Applying the ConfigMap alone does not trigger that rollout. Do not restart before every request.

## Troubleshooting and evidence

- ConfigMap not found or mount failure: apply client/ first; inspect the Pod events and ConfigMap name/namespace.
- Ruby cannot find /tools/ask.rb: compare the key, mountPath, and launcher path.
- Old script behavior: apply the updated ConfigMap and use the restart-and-wait sequence.
- ImagePullBackOff: inspect image download events; this client uses the plain Ruby image rather than the imported office image.
- Client requests time out during policy experiments: check role=client is present and inspect the policy selectors.
- Permission denied for ./bin/ask: check its executable bit and Unix line endings.
